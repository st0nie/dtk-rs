Source-verified (dtkcore/dtkgui 6.7.47) pitfalls handled in dtk-rs:
- `DSettings::setOption(key, v)` does `option(key)->setValue(v)`: null deref for unknown keys; generated shim guards via tools/native_rules.py. `DSettings::fromJson*` returns QPointer(new DSettings) parentless = caller-owned. `setBackend` moves the backend to a new QThread joined on `DSettings::destroyed` but never deletes the backend: dtk-rs `core_settings_set_file_backend` connects `backend->thread()` finished -> backend deleteLater.
- DTK `DFileWatcher` uses a `Q_GLOBAL_STATIC(DFileSystemWatcher)` whose QSocketNotifier is bound to the FIRST QCoreApplication's event dispatcher: it delivers only in the first application scope of a process (verified by core_extras_selfcheck); owned `DFileSystemWatcher` works in every scope.
- On a real X11 session `DNativeSettings`/`DPlatformTheme` install a dynamic QMetaObject, so `qobject_cast<DPlatformTheme*>` returns null (offscreen works). Generated signal connectors use `dynamic_cast` (DTK exports typeinfo). Test GUI selfchecks with `DISPLAY=:0` too, not only offscreen; never call DPlatformTheme/DNativeSettings setters in tests on a real session (they write desktop XSETTINGS).
- DGui headers `ddesktopservices.h` collide with deprecated DWidget ones that come first on the include path; gen.py includes DTK CamelCase forwarding headers (`<DDesktopServices>`) for DCore/DGui classes.
- `DDesktopServices` statics create a function-static QDBusInterface: generated wrappers require the GUI application (`STATIC_REQUIRES_APPLICATION` in gen.py).
